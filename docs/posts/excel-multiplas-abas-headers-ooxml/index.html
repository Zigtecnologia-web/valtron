Quando o Excel não segue o padrão: múltiplas abas, headers deslocados e OOXML

Nas últimas evoluções do Valtron, comecei a trabalhar em um problema que parece simples até aparecer um arquivo real: importar Excel com várias abas sem perder performance nem interpretar a estrutura de forma errada.

Até então, o fluxo estava muito focado em arquivos tabulares mais previsíveis.

Só que Excel do mundo real costuma ser diferente.

Um workbook pode ser várias fontes de dados

Um único .xlsx pode ter:

financeiro.xlsx

├── Clientes
├── Vendas
├── Parcelas
├── Pagamentos
└── Resumo

Cada aba pode representar um conjunto de dados diferente.

Por isso, o Valtron passou a identificar as sheets do workbook e permitir escolher:

☑ Clientes
☑ Vendas
☐ Parcelas
☑ Pagamentos

3 planilhas selecionadas

Também passou a fazer sentido permitir que essas abas sejam organizadas juntas.

Se várias sheets vieram do mesmo arquivo, o usuário pode escolher:

Workspace atual
Outro workspace
Criar novo workspace

Por exemplo:

financeiro.xlsx
      ↓
Clientes
Vendas
Pagamentos
      ↓
Workspace: Financeiro 2026

Mas existe uma separação importante:

o workbook é a origem. O workspace é organização.

O Valtron não deve assumir automaticamente que todo Excel precisa virar um workspace.

O problema não terminou nas abas

Depois disso apareceu um caso mais interessante.

Algumas planilhas tinham estruturas assim:

TABELA DE PARCELADOS

QTO | MUNICÍPIO | Nº SEI | PROGRAMA | VALOR | PARCELAS
1   | Salvador  | ...    | ...      | ...   | ...

Para uma pessoa, está claro que:

TABELA DE PARCELADOS

é apenas um título.

Mas um importador pode interpretar aquela primeira linha como cabeçalho.

Em outras abas, encontrei algo ainda diferente:

linha vazia
linha vazia
linha vazia
TABELA DE PARCELADOS
QTO | MUNICÍPIO | Nº SEI | PROGRAMA | VALOR | ...
dados...

Nesse caso, o cabeçalho real estava na quinta linha.

Assumir:

primeira linha = cabeçalho

simplesmente não funciona para muitos arquivos produzidos para uso humano.

Detectar o cabeçalho sem ler o arquivo inteiro

Uma solução seria abrir toda a sheet em Rust e procurar onde a tabela começa.

Mas isso iria contra uma das principais decisões de arquitetura do Valtron.

Eu não quero:

XLSX
↓
Rust lê 600 mil linhas
↓
Rust analisa tudo
↓
DuckDB lê 600 mil linhas novamente

Então o fluxo ficou mais econômico:

XLSX
↓
descobrir as sheets
↓
usuário seleciona
↓
inspecionar poucas linhas
↓
detectar header provável
↓
detectar largura da tabela
↓
DuckDB faz a leitura pesada

Se uma sheet possui 1 milhão de registros, descobrir onde está o cabeçalho não deveria exigir analisar 1 milhão de linhas.

A quantidade total do dataset não precisa determinar o custo dessa etapa.

E então apareceu um bug ainda mais curioso

Durante os testes, usei dois arquivos XLSX válidos.

Um deles funcionava normalmente.

O outro simplesmente não era reconhecido pelo Valtron.

Curiosamente, o DuckDB conseguia importar os dois sem problemas.

Isso ajudou a isolar a falha.

O problema estava antes do DuckDB.

Nem todo OOXML é escrito da mesma forma

Um XLSX é, na prática, um pacote ZIP contendo vários arquivos XML.

Um dos arquivos que funcionava possuía elementos assim:

<workbook>
<sheet>
<worksheet>
<row>
<c>
<v>

O outro utilizava:

<x:workbook>
<x:sheet>
<x:worksheet>
<x:row>
<x:c>
<x:v>

Semanticamente, os elementos são os mesmos.

A diferença é o prefixo de namespace XML.

Só que o parser auxiliar do Valtron estava procurando literalmente:

sheet
row
c
v

Quando encontrava:

x:sheet
x:row
x:c
x:v

não reconhecia.

O resultado era algo parecido com:

O arquivo não possui planilhas.

mesmo quando o arquivo tinha seis.

A correção não foi adicionar x:

Seria fácil fazer:

sheet OU x:sheet

Mas isso resolveria apenas aquele arquivo.

Outro gerador de XLSX poderia produzir:

<main:sheet>

ou:

<ns1:sheet>

A solução correta foi trabalhar com o nome local do elemento.

Assim:

sheet       → sheet
x:sheet     → sheet
main:sheet  → sheet
ns1:sheet   → sheet

O mesmo para:

x:row → row
x:c   → c
x:v   → v

A ideia é interpretar o significado do elemento, e não depender da forma específica como o prefixo foi escrito.

Compatibilidade sem abandonar performance

Esse tipo de correção é exatamente o que quero preservar no Valtron.

Seria possível resolver muitos casos criando um parser Excel cada vez mais completo dentro do backend Rust.

Mas isso começaria a duplicar trabalho que o DuckDB já faz muito bem.

O papel do parser auxiliar continua pequeno:

descobrir workbook
↓
descobrir sheets
↓
identificar estrutura inicial
↓
entregar o trabalho pesado ao DuckDB

Não:

interpretar o XLSX inteiro

O princípio continua o mesmo:

Inspecionar pouco. Importar com DuckDB.

O erro silencioso também precisava ser corrigido

Esse caso mostrou outro problema importante.

Quando a inspeção falhava, o usuário praticamente não recebia informação útil.

Isso não é aceitável em uma ferramenta de dados.

Agora as etapas precisam ser diferenciadas:

inspeção do workbook
detecção do header
leitura pelo DuckDB
criação do documento

Se uma delas falhar, a interface precisa dizer em qual parte o processo parou.

Por exemplo:

Não foi possível ler a estrutura deste arquivo Excel.

é muito diferente de:

O arquivo não possui planilhas.

Uma coisa é ausência de dados.

Outra é falha de interpretação.

Arquivos reais sempre encontram os nossos pressupostos

Essa implementação me lembrou uma coisa comum em engenharia de dados.

Quando criamos um parser ou pipeline, começamos com alguns pressupostos:

a primeira linha é o cabeçalho
o XML não tem prefixo
as colunas terminam onde esperamos
o arquivo usa shared strings
a sheet possui dimension

Então chegam os dados reais.

E começam a aparecer:

títulos mesclados
linhas vazias
headers deslocados
namespaces diferentes
strings representadas de outra forma
metadados ausentes

O desafio não é apenas aceitar mais formatos.

É fazer isso sem destruir as decisões que já funcionam bem.

O que ficou no Valtron

Depois dessas mudanças, o fluxo de importação de Excel está ficando mais próximo disso:

Workbook
   ↓
Inspeção leve
   ↓
Sheets
   ↓
Seleção
   ↓
Header
   ↓
Largura tabular
   ↓
DuckDB
   ↓
Documents
   ↓
Workspace

E cada parte possui uma responsabilidade clara.

O workbook informa de onde os dados vieram.

A sheet representa um conjunto tabular.

O document representa esse conjunto dentro do Valtron.

O workspace organiza os documentos.

E o DuckDB continua sendo responsável pelo trabalho pesado.

Para mim, essa foi uma evolução importante porque não adicionou apenas suporte a várias abas.

Ela tornou o importador mais preparado para um fato simples:

planilhas reais raramente seguem exatamente o formato que esperamos.
