Data Quality: entender os dados não significa que eles estão corretos

No último post falei sobre Data Profiling e como comecei a usar o DuckDB para entender melhor as colunas importadas pelo Valtron.

O profiling consegue responder perguntas como:

Quantos valores estão vazios?
Quantos são distintos?
Qual é o tamanho dos valores?
Quais aparecem com mais frequência?
A coluna parece numérica?
Parece uma data?

Só que, depois de implementar isso, apareceu uma diferença importante.

Entender o que existe nos dados não significa saber se os dados estão corretos.

É aí que entra Data Quality.

Uma coluna pode parecer perfeita e ainda estar errada

Imagine uma coluna chamada NOTA:

7.5
8.2
9.0
15.3
6.8

O profiling consegue concluir corretamente:

Tipo provável: Decimal
Preenchimento: 100%

Tecnicamente, está tudo certo.

Todos os valores são números.

Mas existe um problema se a regra do sistema disser:

A nota deve estar entre 0 e 10.

Nesse caso:

15.3

é um valor perfeitamente numérico e, ao mesmo tempo, um dado inválido.

Essa diferença fez sentido para separar duas responsabilidades no Valtron: 

PROFILING
"O que existe?"

QUALITY
"O que existe está de acordo
com o que eu espero?"

CPF é outro bom exemplo

Considere:

03000484590
12345678901
11111111111
3000484590

O profiling pode descobrir:

Tipo provável: Texto

Comprimento predominante: 11

Valores preenchidos: 100%

Mas ainda existem outras perguntas:

Possui exatamente 11 dígitos?

É um CPF matematicamente válido?

Está duplicado?

É obrigatório?

Ter 11 dígitos não torna um CPF válido.

Da mesma forma, conseguir converter algo para número não significa que aquilo deveria ser um número.

Data Quality começa quando existe uma expectativa sobre o dado.

Foi daí que surgiram as regras

No Valtron, comecei a trabalhar com regras que podem ser associadas às colunas.

Por exemplo:

CPF

✓ Obrigatório
✓ Comprimento = 11
✓ CPF válido
✓ Valor único

Depois o DuckDB pode analisar o documento e retornar algo parecido com: 

CPF

604.270 registros

5.849 vazios
12.421 com tamanho incorreto
18.011 CPFs inválidos
2.182 registros duplicados

Isso muda bastante a forma de investigar um arquivo.

Em vez de descobrir um problema por acaso enquanto navego pela planilha, consigo perguntar explicitamente:

Quais registros não respeitam minhas regras?

O banco já consegue fazer boa parte disso

Assim como aconteceu com profiling, muitas validações podem ser expressas em SQL.

Para verificar valores obrigatórios:

SELECT COUNT(*)
FROM documento
WHERE cpf IS NULL
   OR TRIM(cpf) = '';

Para comprimento:

SELECT COUNT(*)
FROM documento
WHERE LENGTH(TRIM(cpf)) <> 11;

Para duplicidades:

SELECT cpf, COUNT(*)
FROM documento
GROUP BY cpf
HAVING COUNT(*) > 1;

O interessante não é inventar outra maneira de executar essas operações.

É criar uma camada que organize essas consultas como regras de qualidade. 

Regra visual
     ↓
Valtron
     ↓
condição conhecida
     ↓
DuckDB
     ↓
violações

O usuário trabalha com o conceito:

CPF deve ser único

e não necessariamente com:

GROUP BY cpf
HAVING COUNT(*) > 1

E quem conhece SQL?

Continua podendo usar SQL.

Essa é uma característica que quero preservar.

A interface não precisa substituir SQL.

Ela pode funcionar como uma camada acima dele.

Quem quer investigar visualmente pode usar:

Qualidade
→ CPF válido
→ 18.011 violações
→ Ver registros

Quem prefere SQL continua tendo o console disponível.

São maneiras diferentes de chegar aos mesmos dados.

As regras precisam ser explícitas

Uma decisão importante foi não tentar adivinhar automaticamente todas as regras.

Imagine uma coluna:

IDADE

O Valtron poderia perceber que ela contém números.

Mas qual seria o intervalo válido?

0 a 100?
0 a 120?
18 a 65?

Depende do contexto.

Ou uma coluna:

STATUS

Talvez os valores válidos sejam:

ATIVO
INATIVO

Em outro sistema poderiam ser:

PENDENTE
APROVADO
REPROVADO
CANCELADO

O profiling consegue ajudar a descobrir o que existe.

Mas a regra de negócio precisa vir de algum lugar.

Por isso prefiro que a primeira versão das regras seja determinística e explícita.

Algumas regras são genéricas

Existem validações que fazem sentido em muitos contextos:

Obrigatório
Único
Comprimento
Numérico
Intervalo numérico
Valores permitidos
Data válida
Expressão regular
E-mail válido
CPF válido

Então posso configurar:

NOTA

Regra:
Intervalo numérico

Mínimo: 0
Máximo: 10

ou:

TURNO

Valores permitidos:

MATUTINO
VESPERTINO
NOTURNO

O Valtron não precisa conhecer o sistema que gerou o arquivo.

Ele só precisa saber executar a regra.

Datas mostraram um caso interessante

Durante os testes encontrei valores como:

33639

em uma coluna de data de nascimento.

Uma validação configurada para:

YYYY/MM/DD

naturalmente considera 33639 inválido.

Só que esse número pode representar uma data no sistema de datas do Excel.

Isso mostrou outro cuidado importante.

Uma regra precisa saber distinguir:

valor armazenado

de:

valor interpretado

O Valtron pode reconhecer:

33639
↓
Serial de data do Excel
↓
data válida

sem alterar o 33639 original.

Essa separação entre interpretar, validar e transformar começou a aparecer várias vezes durante o desenvolvimento.

Uma linha pode quebrar várias regras

Outro problema interessante apareceu quando comecei a pensar no score de qualidade.

Imagine:

CPF = ""

Esse registro pode violar:

Obrigatório
Comprimento = 11
CPF válido

Se simplesmente somarmos todas as violações, teremos três problemas.

Mas existe apenas uma linha problemática.

Então existem duas métricas diferentes:

Violações de regras

e:

Registros com pelo menos um problema

Isso importa bastante para calcular um indicador geral.

Imagine:

604.270 registros

36.281 possuem pelo menos
um problema

O score pode ser calculado sobre as linhas válidas:

567.989 / 604.270

≈ 94%

Sem contar a mesma linha três ou quatro vezes.

O número sozinho também pode enganar

Mostrar:

Qualidade: 99%

parece excelente.

Mas em uma base com 4 milhões de registros, 1% significa:

40.000 registros

Por isso quero evitar depender apenas de cores ou percentuais.

Prefiro algo como:

QUALIDADE

99%

4.000.000 registros
40.000 com problemas

Percentual fornece proporção.

Quantidade fornece dimensão.

Os dois juntos contam melhor a história.

Clicar no problema precisa mostrar o problema

Assim como no profiling, quero evitar um painel que apenas apresenta números.

Se o Valtron disser:

CPF inválido
18.011 violações

esse número precisa ser clicável.

O fluxo:

CPF inválido
18.011
    ↓
clique
    ↓
grid filtrada
    ↓
18.011 registros

A mesma condição utilizada para contar as violações precisa ser usada para filtrar a grid.

Isso parece detalhe de implementação, mas evita uma situação bastante ruim: 

Painel:
18.011 problemas

Grid:
17.982 registros

Quando uma ferramenta analisa qualidade de dados, os próprios resultados dela precisam ser confiáveis.

Encontrar não significa corrigir

Essa talvez seja a separação mais importante até agora.

Se o Valtron encontrar:

12.391 CPFs com pontuação

ele não deveria simplesmente alterar:

030.004.845-90

para:

03000484590

Só porque parece uma correção óbvia.

Primeiro:

IDENTIFICAR

Depois:

VALIDAR

E somente com intenção explícita:

TRANSFORMAR

Essa separação ajuda a evitar que uma ferramenta criada para analisar dados acabe modificando silenciosamente aquilo que deveria apenas investigar.

O fluxo começou a ficar mais claro

Com Data Quality, comecei a enxergar o Valtron menos como um visualizador de arquivos e mais como uma ferramenta de preparação de dados.

O fluxo está ficando assim:

ARQUIVO
   ↓
IMPORTAR
   ↓
EXPLORAR
   ↓
PROFILE
   ↓
"O que existe?"
   ↓
QUALITY
   ↓
"O que está errado?"
   ↓
TRANSFORM
   ↓
"Como quero corrigir?"
   ↓
EXPORTAR

Cada etapa tem uma responsabilidade.

E isso leva naturalmente ao próximo problema.

Se eu descubro que existem 12 mil datas em serial do Excel, 8 mil CPFs sem padding e milhares de nomes com espaços extras, como corrigir tudo isso sem editar milhares de células manualmente?

É aí que entram as transformações em massa.
