Por que o Valtron importa os dados como texto antes de tentar entendê-los

Quando comecei a trabalhar na importação do Valtron, tomei uma decisão que pode parecer estranha:

as colunas de um arquivo são inicialmente importadas como texto.

Mesmo quando os valores parecem números, datas ou valores decimais.

Por exemplo:

NOME            NOTA        NASCIMENTO
João            8.5         1992-02-05
Maria           9.2         33639
Pedro           7           05/10/1995

Seria natural transformar imediatamente:

NOTA        → DECIMAL
NASCIMENTO  → DATE

Mas existe um problema.

Dados reais nem sempre são tão organizados quanto parecem.

O arquivo diz menos do que imaginamos

Considere uma coluna chamada CPF:

03000484590
3000484590
123.456.789-00
NULL

O que ela é?

Para uma pessoa, parece óbvio que estamos olhando CPFs.

Para o computador, são apenas valores.

Agora imagine uma coluna:

CODIGO

000123
000124
000125

Se eu inferir automaticamente que isso é um número, posso transformar:

000123

em:

123

Tecnicamente o número é equivalente.

Para o dado original, talvez não seja.

Os zeros podem fazer parte do identificador.

Datas conseguem ser ainda mais interessantes

Recentemente encontrei um bom exemplo disso.

Uma coluna de data de nascimento continha:

33639

Olhando isoladamente, parece apenas um inteiro.

Mas esse valor pode representar uma data armazenada como serial do Excel.

Ou seja:

33639

pode ser interpretado como uma data no sistema utilizado pelo Excel.

Agora imagine que durante a importação eu simplesmente decida:

33639 → INTEGER

A informação não necessariamente foi perdida, mas a decisão sobre o significado daquele valor foi tomada cedo demais.

E esse é exatamente o tipo de decisão que comecei a evitar no Valtron.

Armazenar é diferente de interpretar

Passei a separar duas coisas:

VALOR ORIGINAL
      ↓
   "33639"

INTERPRETAÇÃO
      ↓
possível serial de data do Excel

O primeiro pertence ao armazenamento.

O segundo pertence à análise.

Essa separação é importante.

O Valtron pode dizer:

DATA_NASCIMENTO

Tipo provável:
Data

Formato predominante:
Serial de data do Excel

sem precisar modificar:

33639

para:

05/02/1992

O dado continua intacto.

A interpretação pode evoluir.

É por isso que uso all_varchar

No caminho principal de importação XLSX, o Valtron utiliza o read_xlsx do DuckDB com all_varchar = true. As colunas importadas são preservadas inicialmente como VARCHAR.

Conceitualmente:

CREATE TABLE documento AS
SELECT *
FROM read_xlsx(
    'arquivo.xlsx',
    header = true,
    all_varchar = true
);

Isso significa que valores como:

000123
8.50
33639
03000484590

podem ser preservados sem o Valtron tentar decidir imediatamente o que representam.

Depois entra outra camada.

Data Profiling

Depois que os dados estão no DuckDB, o Valtron pode começar a fazer perguntas.

Por exemplo:

Quantos valores estão vazios?

Quantos são distintos?

Os valores parecem números?

Parecem datas?

Qual o tamanho mínimo e máximo?

Quais valores aparecem com mais frequência?

É aí que entra o Data Profiling.

Em vez de decidir durante a importação:

essa coluna É decimal

o Valtron pode concluir:

essa coluna PARECE decimal

Existe uma diferença importante entre as duas frases.

A primeira altera a forma como o dado será armazenado.

A segunda fornece informação para o usuário tomar uma decisão.

Inferência precisa aceitar que pode estar errada

Imagine:

NOTA

8.5
7.2
9.1
10
NÃO INFORMADO
8.0

A maior parte dos valores parece decimal.

Mas existe:

NÃO INFORMADO

Se eu tentar converter a coluna inteira durante a importação, preciso decidir o que fazer com esse registro.

Falhar a importação?

Transformar em NULL?

Ignorar?

Modificar o valor?

Qualquer uma dessas opções já é uma decisão sobre os dados.

No profiling posso simplesmente dizer:

NOTA

Decimal provável

99,8% compatíveis
0,2% incompatíveis

E deixar o usuário investigar os casos restantes.

Isso me parece muito mais seguro.

Profiling e tipagem são coisas diferentes

Esse conceito começou a ficar importante na arquitetura do Valtron.

TIPO FÍSICO

VARCHAR

       ↓

PROFILING

99,8% dos valores
parecem decimais

       ↓

TIPO PROVÁVEL

Decimal

O tipo físico diz como o valor está armazenado.

O tipo provável diz como o Valtron interpreta aquele conteúdo.

Essas duas informações não precisam ser iguais.

Depois vem Data Quality

Quando sabemos o que uma coluna provavelmente representa, podemos começar a perguntar se os valores fazem sentido.

Por exemplo:

CPF

604.270 registros

5.849 vazios
12.421 com tamanho incorreto
18.011 inválidos
2.182 duplicados

Isso já é diferente de profiling.

Profiling pergunta:

O que existe aqui?

Data Quality pergunta:

O que existe aqui respeita as regras que eu espero?

Um CPF pode estar armazenado perfeitamente como texto e ainda ser um CPF inválido.

Uma nota pode ser perfeitamente convertível para decimal e ainda possuir valor: 

15.7

quando a regra aceita apenas:

0 até 10

Tipagem e qualidade também são problemas diferentes.

E só depois vem transformação

Essa separação começou a formar um fluxo que gosto bastante:

IMPORTAR
   ↓
PRESERVAR
   ↓
ANALISAR
   ↓
VALIDAR
   ↓
TRANSFORMAR

Por exemplo:

CPF original

030.004.845-90

O Valtron pode primeiro identificar:

Texto provável
14 caracteres
formatação presente

Depois validar:

CPF válido?

E somente quando o usuário decidir transformar:

030.004.845-90

       ↓

Remover pontuação

       ↓

03000484590

Nesse momento existe uma intenção explícita de modificar o dado.

Preview antes de alterar

Essa ideia também está direcionando a parte de transformação que estou desenvolvendo.

Antes de modificar centenas de milhares de registros, quero que o Valtron consiga mostrar algo assim: 

NORMALIZAR CPF

Original             Resultado
────────────────────────────────
030.004.845-90       03000484590
123.456.789-00       12345678900
3000484590           03000484590

12.391 valores serão alterados

[ Cancelar ]    [ Aplicar ]

A diferença é que agora a transformação não aconteceu porque um algoritmo decidiu durante a importação.

Ela aconteceu porque o usuário viu o impacto e decidiu aplicar.

O princípio que ficou

No começo, all_varchar = true era principalmente uma decisão técnica relacionada à importação.

Com a evolução do Valtron, percebi que ela também combina com uma decisão de produto.

Preservar primeiro. Interpretar depois. Transformar somente quando houver intenção.

Isso não significa que armazenar tudo como texto seja a melhor estratégia para qualquer sistema.

Em um sistema transacional, eu quero tipos fortes, constraints e regras bem definidas no banco.

Mas o Valtron recebe arquivos que ele não conhece previamente.

É um cenário diferente.

Quando alguém entrega uma planilha com 600 mil registros, eu prefiro que o Valtron comece perguntando:

O que existe nesses dados?

em vez de começar afirmando:

Eu já sei o que esses dados significam.

No próximo post quero entrar justamente nessa etapa: como o Data Profiling pode ajudar a entender centenas de milhares de registros sem precisar escrever várias consultas SQL manualmente.
