DuckDB 2.0 e os próximos caminhos para o Valtron

O Valtron nasceu com uma decisão importante de arquitetura: utilizar o DuckDB como motor de processamento local.

Essa escolha permite importar, consultar e transformar grandes volumes de dados diretamente no computador do usuário, sem depender de um servidor para cada operação.

Agora, com o DuckDB 2.0 no horizonte, algumas das novidades apresentadas pelo projeto abrem possibilidades interessantes para o futuro do Valtron.

A prévia publicada pelo DuckDB cita recursos como DuckDB como servidor, I/O assíncrono e um novo parser SQL. O interessante, para o Valtron, não é trocar a arquitetura inteira, mas entender quais caminhos passam a ficar possíveis.

DuckDB além do processamento local

Uma das novidades que mais chama atenção é o Quack.

Historicamente, uma das principais características do DuckDB sempre foi funcionar dentro da própria aplicação.

No Valtron, a arquitetura segue essa ideia:

Valtron
   ↓
Rust
   ↓
DuckDB
   ↓
Dados locais

O arquivo está no computador, o processamento acontece localmente e apenas o resultado necessário é apresentado pela interface.

Com o Quack, começa a surgir outra possibilidade: comunicação entre instâncias do DuckDB através da rede.

Isso permitiria pensar em algo como:

Valtron Desktop
       ↓
     Quack
       ↓
DuckDB remoto
       ↓
 Grandes datasets

Isso não significa abandonar o processamento local.

Na verdade, os dois modelos podem coexistir.

Para arquivos que estão no computador:

Valtron
   ↓
DuckDB local

Para datasets muito maiores armazenados em outra infraestrutura:

Valtron
   ↓
DuckDB remoto

O interessante é que o Valtron poderia continuar sendo uma aplicação desktop enquanto parte do processamento acontece perto dos dados.

Processar perto dos dados

Imagine um dataset fictício com dezenas de gigabytes armazenado em um servidor.

Trazer tudo para o computador apenas para responder uma pergunta seria desperdício:

80 GB
  ↓
transferência
  ↓
Valtron
  ↓
processamento

Seria muito mais eficiente enviar a consulta:

SELECT
    categoria,
    SUM(valor) AS total
FROM vendas
GROUP BY categoria;

e receber somente o resultado:

DuckDB remoto
      ↓
processa milhões de registros
      ↓
retorna algumas dezenas de linhas
      ↓
Valtron

Essa separação entre onde está a interface e onde acontece o processamento pode ser bastante interessante para o futuro do projeto.

Um Console SQL mais inteligente

Outra novidade importante é o novo parser SQL baseado em PEG.

Isso conversa diretamente com uma área que está evoluindo no Valtron: o Console SQL.

Considere um dataset fictício:

produto
categoria
quantidade
preco
data_venda

O usuário poderia escrever:

SELECT
    categoria,
    SUM(preco) AS total
FROM documento
GROUP BY categoria;

Mas erros acontecem.

Alguém poderia escrever:

SELECT categorias
FROM documento;

quando a coluna correta é:

categoria

Em vez de simplesmente apresentar um erro técnico do banco, o Valtron pode utilizar as informações fornecidas pelo DuckDB para construir uma experiência melhor:

Coluna "categorias" não encontrada.

Você quis dizer "categoria"?

O princípio aqui é importante:

o DuckDB entende SQL; o Valtron transforma essa informação em uma experiência melhor para o usuário.

Não precisamos construir outro parser SQL dentro do Valtron se o próprio motor consegue fornecer informações suficientes.

Autocomplete baseado no dataset

O Console SQL também pode combinar o parser com o schema conhecido pelo Valtron.

Se um documento possuir:

produto
categoria
quantidade
preco
data_venda

ao começar a escrever:

SELECT cat

o editor pode sugerir:

categoria

Da mesma forma, ao utilizar uma coluna com espaços, o Valtron pode inserir automaticamente o identificador corretamente.

A ideia é manter SQL de verdade, mas diminuir o conhecimento necessário para começar a utilizá-lo.

I/O assíncrono

Outra evolução importante apresentada para o DuckDB envolve operações assíncronas de entrada e saída.

Isso se torna particularmente relevante quando os dados não estão mais no SSD local.

Hoje podemos pensar no Valtron principalmente assim:

Valtron
├── XLSX
├── CSV
└── Parquet

No futuro, esse conjunto poderia crescer:

Valtron
├── Arquivos locais
│   ├── XLSX
│   ├── CSV
│   └── Parquet
│
└── Fontes remotas
    ├── Object Storage
    ├── Parquet remoto
    └── DuckDB remoto

Quanto mais distante o dado estiver fisicamente da aplicação, mais importante se torna reduzir espera e aproveitar melhor as operações de I/O.

Parquet fica ainda mais interessante

Essa evolução também reforça um formato que faz bastante sentido para o Valtron: Parquet.

Um fluxo poderia começar com:

dados.xlsx

passar por:

XLSX
 ↓
Valtron
 ↓
DuckDB
 ↓
limpeza
 ↓
SQL
 ↓
transformação

e terminar em:

dados_tratados.parquet

Esse novo dataset poderia ser utilizado posteriormente sem precisar retornar ao formato original.

Para grandes volumes, isso cria uma ponte interessante entre o mundo das planilhas e ferramentas de engenharia e análise de dados.

Transformações como documentos

Existe ainda outra direção que considero especialmente interessante.

Hoje uma consulta SQL normalmente produz um resultado temporário:

Documento
    ↓
Consulta SQL
    ↓
Resultado

Mas e se o resultado pudesse virar outro documento?

Documento original
        ↓
      SQL
        ↓
Novo documento

Por exemplo, um dataset fictício contendo vendas poderia gerar diferentes conjuntos:

vendas
  │
  ├──→ vendas_validas
  │
  ├──→ produtos
  │
  └──→ resumo_mensal

Se o Valtron também guardar qual consulta produziu cada documento, começamos a ter algo ainda mais interessante:

dataset A
    ↓
transformação
    ↓
dataset B

A partir daí conceitos como lineage, pipelines e organização de dados começam a surgir naturalmente.

E as camadas Bronze, Silver e Gold?

Em uma evolução posterior, essas transformações poderiam ser organizadas utilizando conceitos da arquitetura medalhão.

Por exemplo:

Fonte
  ↓
Bronze
  ↓
Silver
  ↓
Gold

Bronze poderia preservar os dados próximos da origem.

Silver poderia representar dados tratados, tipados, normalizados e relacionados.

Gold poderia representar datasets preparados para análise, indicadores ou visualizações.

O importante é não implementar Bronze, Silver e Gold apenas como etiquetas.

Primeiro precisamos ter uma boa estrutura de transformação entre datasets.

Depois, as camadas passam a organizar algo que já funciona.

Local e remoto podem coexistir

Talvez uma das possibilidades mais interessantes dessa evolução do DuckDB seja não precisar escolher entre uma aplicação local e uma infraestrutura remota.

Podemos imaginar:

Valtron
                       │
             ┌─────────┴─────────┐
             │                   │
           Local               Remoto
             │                   │
           DuckDB              Quack
             │                   │
      arquivos locais      DuckDB remoto

Um arquivo pequeno ou médio continua sendo processado diretamente no computador.

Um dataset muito maior pode permanecer em uma máquina preparada para isso.

O usuário continua trabalhando na mesma interface.

O que muda é onde o trabalho pesado acontece.

Ainda não é hora de mudar tudo

Algumas dessas tecnologias ainda estão evoluindo.

Por isso, não faria sentido alterar toda a arquitetura do Valtron agora apenas para acompanhar as novidades.

Existe uma sequência mais segura:

Console SQL
    ↓
contexto por documento
    ↓
autocomplete e melhores erros
    ↓
consultas salvas
    ↓
resultado como novo documento
    ↓
transformações
    ↓
lineage
    ↓
pipelines

Depois disso, podemos avaliar recursos maiores:

fontes externas
      ↓
processamento remoto
      ↓
orquestração
      ↓
arquitetura medalhão

O que mais chama atenção no DuckDB 2.0

Para o Valtron, talvez o ponto mais interessante não seja uma funcionalidade específica.

É a direção que o DuckDB está tomando.

O projeto continua extremamente forte como banco analítico embarcado, mas começa a expandir os cenários em que esse mesmo motor pode operar.

Isso abre uma possibilidade interessante para o Valtron:

crescer sem abandonar sua arquitetura local.

Podemos continuar oferecendo uma experiência rápida para quem simplesmente quer abrir e explorar um arquivo, enquanto construímos gradualmente recursos para transformações, datasets maiores e processamento remoto.

Se essa evolução continuar, o DuckDB deixa de ser apenas o motor que permite ao Valtron abrir arquivos rapidamente.

Ele pode se tornar a base para uma plataforma local de exploração e transformação de dados muito mais completa.
