Por que comecei a desenvolver o Valtron

O Valtron começou a partir de um problema relativamente simples: trabalhar com arquivos de dados grandes no desktop sem transformar isso em um processo complicado.

Planilhas funcionam muito bem para uma quantidade enorme de situações. O problema começa quando o volume cresce.

Um arquivo com centenas de milhares de linhas pode até abrir, mas abrir o arquivo é apenas uma parte do problema. Depois você precisa navegar pelos dados, filtrar, ordenar, procurar inconsistências, fazer consultas e, eventualmente, alterar ou exportar alguma coisa.

Foi a partir desse cenário que comecei a desenvolver o Valtron.

A ideia inicial

O objetivo era construir uma aplicação desktop capaz de importar arquivos grandes e permitir trabalhar com eles localmente.

Sem precisar subir o arquivo para algum serviço.

Sem precisar configurar um banco de dados externo.

Sem precisar criar um script diferente toda vez que eu quisesse investigar alguma coisa.

O fluxo deveria ser simples:

XLSX / CSV
     ↓
   Valtron
     ↓
 explorar os dados

Só que rapidamente percebi que importar rápido não seria suficiente.

Se eu conseguisse carregar 600 mil linhas em poucos segundos, mas a interface travasse tentando renderizar tudo, eu apenas teria movido o gargalo de lugar.

Foi aí que o projeto começou a ficar mais interessante.

DuckDB como motor local

Escolhi o DuckDB como banco local do Valtron.

A ideia combina bastante com o tipo de aplicação que eu queria construir. Em vez de precisar manter um PostgreSQL ou outro servidor rodando, o banco fica embutido na própria aplicação.

O arquivo entra e vira uma tabela local no DuckDB.

Hoje, cada documento importado pelo Valtron é persistido dessa forma.

Isso permite usar SQL para fazer boa parte do trabalho pesado:

SELECT COUNT(*)
FROM documento;

ou:

SELECT cidade, COUNT(*)
FROM documento
GROUP BY cidade;

A interface não precisa conhecer centenas de milhares de registros de uma vez. Ela pede ao DuckDB apenas aquilo de que precisa.

A interface também precisava ser econômica

Essa foi outra parte importante do projeto.

Se existem 600 mil registros, não existe motivo para criar 600 mil elementos HTML se o usuário consegue enxergar talvez 20 ou 30 linhas naquele momento.

Por isso a grid do Valtron é virtualizada.

Ela trabalha com pequenos lotes de dados e mantém em memória somente as regiões próximas daquela que está sendo visualizada. Atualmente o Valtron trabalha com lotes de 100 linhas, overscan e cache limitado de lotes.

A lógica é basicamente:

600.000 registros no DuckDB

          ↓

buscar somente uma pequena janela

          ↓

renderizar o que o usuário precisa ver

Parece uma diferença pequena, mas muda completamente o comportamento da aplicação.

O Valtron começou a crescer

Depois que importação e navegação ficaram funcionando bem, começaram a aparecer outras necessidades.

Hoje já consigo organizar documentos em workspaces, filtrar e ordenar dados, escolher as colunas visíveis, redimensionar colunas, editar células, executar consultas SQL e exportar documentos novamente para CSV, TSV ou XLSX.

Mais recentemente comecei a trabalhar também com profiling e qualidade dos dados.

A ideia deixou de ser apenas:

abrir um arquivo grande.

E passou a ser:

abrir, entender e trabalhar com esse arquivo.

Essa diferença está direcionando bastante o desenvolvimento do projeto.

O que o Valtron está se tornando

Hoje penso no Valtron como um pequeno data studio local.

A arquitetura continua relativamente simples:

Tauri
  │
  ├── TypeScript
  │      ↓
  │   Interface
  │
  └── Rust
         ↓
       DuckDB

O Tauri cuida da aplicação desktop, TypeScript da interface, Rust das operações de backend e DuckDB do processamento analítico dos dados.

Ainda há bastante coisa que quero experimentar.

Mas uma das ideias que pretendo preservar é esta:

Os dados ficam locais e o trabalho pesado deve acontecer o mais próximo possível deles.

No próximo post vou entrar em uma das partes que mais me fizeram experimentar durante o desenvolvimento: como importar mais de 600 mil registros de um XLSX em poucos segundos e por que algumas tentativas de otimização deixaram o processo mais lento.

Como carreguei mais de 600 mil registros em poucos segundos

Um dos primeiros desafios que coloquei para o Valtron foi importar rapidamente um arquivo XLSX grande.

O arquivo que usei nos testes tinha 604.270 linhas e 13 colunas.

Minha pergunta inicialmente parecia simples:

Qual é a maneira mais rápida de colocar esses dados no DuckDB?

A resposta acabou sendo menos óbvia do que eu imaginava.

A primeira ideia

Como o backend do Valtron é escrito em Rust, um caminho natural seria abrir o XLSX no Rust, percorrer as células, tratar os valores e depois inserir os dados no DuckDB.

Algo parecido com:

XLSX
  ↓
Rust lê planilha
  ↓
converte os dados
  ↓
DuckDB

Tecnicamente funciona.

O problema é que existe um custo escondido nesse processo.

O Rust precisa abrir e percorrer o arquivo. Depois os dados precisam ser convertidos e enviados para o banco.

Quando estamos falando de algumas centenas de linhas, isso provavelmente não chama atenção.

Com mais de 600 mil, começa a aparecer.

Testando outras estratégias

Durante o desenvolvimento experimentei caminhos diferentes.

Entre eles:

XLSX → Rust → CSV → DuckDB

Também:

XLSX → Rust → Appender → DuckDB

E:

XLSX → DuckDB read_xlsx

Foi importante medir cada etapa separadamente.

Não bastava saber que uma importação levou 20 segundos. Eu queria descobrir onde os 20 segundos estavam sendo gastos.

Por isso comecei a registrar métricas como:

abertura do XLSX
leitura da planilha
conversão
geração de CSV
DuckDB
Appender
commit
tempo total

Essa instrumentação acabou mudando algumas decisões do projeto.

Uma otimização que piorou a performance

Em determinado momento havia uma etapa em Rust que abria o XLSX antes do DuckDB.

A intenção era boa. Eu poderia descobrir informações sobre a planilha, validar algumas coisas e preparar o processo de importação.

Só havia um problema.

Depois disso, o DuckDB precisava abrir o mesmo XLSX novamente para realmente importar os dados.

Na prática:

arquivo.xlsx
    ↓
Rust abre e percorre
    ↓
~5 segundos
    ↓
DuckDB abre novamente
    ↓
importação

Eu estava fazendo trabalho duas vezes.

A documentação atual do Valtron inclusive protege essa decisão arquitetural: o caminho padrão não deve abrir previamente a planilha com calamine, percorrer suas células ou gerar um CSV intermediário.

Removendo trabalho

A solução que apresentou o melhor comportamento foi muito mais simples: 

arquivo.xlsx
     ↓
DuckDB read_xlsx
     ↓
tabela

O comando conceitualmente fica próximo de:

CREATE TABLE documento AS
SELECT *
FROM read_xlsx(
    'arquivo.xlsx',
    header = true,
    all_varchar = true
);

O Valtron atualmente utiliza justamente CREATE TABLE ... AS SELECT * FROM read_xlsx(...) no caminho padrão de XLSX/XLSM.

Com isso, eliminei uma passagem completa pelo arquivo.

Por que all_varchar = true?

Outra decisão foi importar inicialmente as colunas como texto.

Pode parecer estranho para uma ferramenta de análise de dados.

Por que uma nota 8.5 não entra diretamente como decimal?

Por que uma data não entra diretamente como DATE?

Porque, nessa etapa, minha prioridade é preservar aquilo que chegou no arquivo e evitar inferências inesperadas.

O Valtron pode posteriormente analisar uma coluna e concluir:

NOTA
Decimal provável

ou:

DATA_NASCIMENTO
Data provável

Mas isso é diferente de modificar a representação do dado durante a ingestão.

Hoje as colunas importadas são armazenadas como texto justamente para manter esse comportamento previsível.

O resultado

Com o caminho direto via read_xlsx, consegui chegar à casa de poucos segundos para importar o arquivo de teste com mais de 600 mil registros.

Mas o resultado mais interessante não foi simplesmente o número do benchmark.

Foi perceber que:

às vezes otimizar significa remover código.

Eu estava procurando uma maneira mais rápida de processar o XLSX em Rust quando, na prática, o melhor resultado apareceu ao deixar de processá-lo duas vezes.

Essa experiência também criou uma regra para o projeto.

O caminho de importação que apresentou o melhor resultado fica protegido. Uma funcionalidade nova de interface, profiling, filtros ou qualidade de dados não deve mexer nele sem uma razão diretamente relacionada à importação e sem um novo benchmark mostrando ganho real.

Isso evita uma situação comum em otimização: melhorar a arquitetura no papel e piorar o tempo no cronômetro.

No próximo post, pretendo falar sobre a outra metade do problema: depois de importar 600 mil registros rapidamente, como mostrar esses dados sem transformar a interface no novo gargalo?

Importar 600 mil linhas rápido não adianta se a interface travar

Nos primeiros testes do Valtron, boa parte da minha atenção estava no tempo de importação.

O objetivo era simples: pegar um XLSX grande, colocar os dados no DuckDB e disponibilizá-los para consulta o mais rápido possível.

Depois de alguns experimentos, consegui chegar a poucos segundos para um arquivo com mais de 600 mil registros.

Só que isso criou outro problema.

O banco conseguia lidar com os dados. A interface também precisava conseguir.

O problema mudou de lugar

Imagine um arquivo com:

604.270 linhas
13 colunas

Isso representa quase 8 milhões de células.

Mesmo que os dados já estejam disponíveis no DuckDB, não faria sentido buscar 604 mil registros e criar milhares ou milhões de elementos HTML para mostrá-los.

Seria algo parecido com:

DuckDB
   ↓
SELECT 600.000 linhas
   ↓
Rust
   ↓
TypeScript
   ↓
DOM
   ↓
problema

Nesse cenário, eu teria uma importação rápida e uma interface lenta.

A otimização só teria mudado o gargalo de lugar.

A grid não precisa conhecer o arquivo inteiro

A pergunta que ajudou a resolver isso foi:

Se o usuário consegue enxergar apenas algumas linhas na tela, por que carregar 600 mil?

A grid do Valtron passou então a trabalhar com virtualização.

A ideia é relativamente simples.

Suponha que o documento tenha:

604.270 registros

mas naquele momento a tela mostre algo próximo de:

20 ou 30 registros

Não existe necessidade de renderizar os outros 604 mil.

O Valtron trabalha com pequenas janelas dos dados:

             604.270 linhas
                   │
                   │
                   ▼
        ┌─────────────────────┐
        │       DuckDB        │
        └──────────┬──────────┘
                   │
             busca 100
                   │
                   ▼
        ┌─────────────────────┐
        │   janela da grid    │
        │                     │
        │ linha 1200          │
        │ linha 1201          │
        │ linha 1202          │
        │ ...                 │
        └─────────────────────┘

Atualmente, a grid utiliza lotes de 100 linhas.

O scroll passa a determinar quais dados são necessários

Conforme o usuário navega, o frontend calcula qual região da tabela deveria estar visível.

Então solicita ao backend apenas aquela janela.

O backend possui uma operação específica para isso e retorna os valores das colunas necessárias, além das informações usadas para saber se existe um próximo lote.

Conceitualmente:

Usuário faz scroll
       ↓
Frontend calcula a região
       ↓
"Preciso das linhas 1200 até 1299"
       ↓
Rust
       ↓
DuckDB
       ↓
100 registros
       ↓
Grid

Assim, o tamanho total do documento deixa de determinar diretamente quantos elementos precisam existir na interface.

Mas buscar somente quando o usuário chega também não é suficiente

Existe outro detalhe.

Se a aplicação esperar o usuário chegar ao final de um lote para só então buscar o próximo, pode aparecer uma pequena pausa durante o scroll.

Por isso implementei prefetch.

Antes de o usuário realmente precisar do próximo conjunto de registros, o Valtron já pode começar a buscá-lo.

O comportamento fica aproximadamente assim:

Lote atual

0 ───────────────────── 100
                  ↑
             usuário

              ↓

Valtron percebe que está
se aproximando do final

              ↓

busca 100 ───────────── 200

Atualmente o prefetch acontece quando a navegação alcança aproximadamente 75% da região configurada.

A intenção é simples: quando o usuário chegar aos próximos registros, eles provavelmente já estarão disponíveis.

Cache também precisa ter limite

Uma solução fácil seria continuar guardando todos os lotes já carregados.

Mas isso recriaria o problema original aos poucos.

Depois de navegar bastante:

100 linhas
200
500
2.000
10.000
50.000
...

a aplicação começaria a acumular dados que o usuário nem está mais vendo.

Por isso o cache também possui limite.

O Valtron mantém os lotes próximos da região atual e pode descartar os mais distantes.

A configuração atual limita o cache a cinco lotes.

A ideia é trabalhar com uma janela móvel:

descartado

[ lote 1 ]

             cache atual

        [ lote 8 ]
        [ lote 9 ]
        [ lote 10 ] ← usuário
        [ lote 11 ]
        [ lote 12 ]

                         [ lote 20 ]
                         ainda nem foi buscado

Isso mantém o consumo de memória mais previsível.

Overscan ajuda a esconder a virtualização

Existe ainda um pequeno detalhe visual.

Se fossem renderizadas somente as linhas exatamente visíveis, um scroll rápido poderia revelar regiões ainda não renderizadas.

Por isso existem algumas linhas adicionais antes e depois da região visível.

É o chamado overscan.

No Valtron, atualmente são utilizadas oito linhas de overscan.

Para o usuário parece uma tabela normal.

Internamente, porém, apenas uma pequena parte dela está realmente sendo renderizada naquele momento.

E filtros e ordenação?

Esse foi outro ponto importante.

Não faria sentido carregar todo o documento no frontend para depois executar:

rows.filter(...)

ou:

rows.sort(...)

Os filtros e a ordenação precisam acontecer próximos dos dados.

Então o frontend envia ao backend informações como:

offset
limit
filtros
ordenação
colunas visíveis

e o DuckDB executa a consulta correspondente.

O resultado volta já preparado para aquela janela.

A divisão de responsabilidades fica aproximadamente assim:

DUCKDB

filtrar
ordenar
paginar
agregar

      ↓

RUST

orquestrar
validar
preparar resposta

      ↓

TYPESCRIPT

virtualizar
cachear
renderizar
interagir

Cada camada faz aquilo em que é melhor.

Colunas também importam

Outra otimização interessante apareceu depois.

Se um documento possui 50 colunas, mas o usuário escolheu visualizar apenas 8, por que transportar as outras 42?

O backend da janela virtualizada consegue receber quais colunas estão visíveis e retornar somente os valores necessários para elas.

É a mesma ideia aplicada em outra direção:

não buscar dados simplesmente porque eles existem.

Buscar aquilo que é necessário naquele momento.

O que aprendi com essa parte do Valtron

Trabalhar com grandes volumes não é apenas fazer o banco responder rápido.

Existe um caminho inteiro:

disco
 ↓
DuckDB
 ↓
Rust
 ↓
serialização
 ↓
TypeScript
 ↓
memória
 ↓
DOM
 ↓
tela

O gargalo pode aparecer em qualquer ponto.

No caso do Valtron, a estratégia acabou ficando baseada em uma regra bastante simples:

o tamanho do dataset não deveria ser o tamanho do trabalho feito pela interface.

Se existem 600 mil linhas no banco e o usuário está olhando 30, a interface deveria trabalhar o máximo possível como se existissem apenas aquelas 30.

DuckDB continua sabendo que existem 600 mil.

A grid não precisa saber de todas ao mesmo tempo.

Foi essa separação que permitiu sair de uma importação rápida para uma navegação que também continua responsiva.

DuckDB dentro de uma aplicação desktop: por que escolhi esse caminho no Valtron

Quando comecei o Valtron, uma das decisões mais importantes foi escolher onde os dados ficariam depois da importação.

Eu poderia carregar o arquivo e manter tudo em memória.

Poderia converter os dados para alguma estrutura própria.

Poderia até exigir que o usuário tivesse PostgreSQL ou outro banco instalado.

Acabei seguindo outro caminho:

usar o DuckDB como banco de dados embutido na própria aplicação.

Isso resolveu mais problemas do que apenas onde armazenar os dados.

O que eu precisava

O Valtron trabalha com arquivos que podem ter centenas de milhares de registros.

Depois de importar um XLSX ou CSV, eu precisava conseguir fazer coisas como: 

SELECT COUNT(*)
FROM documento;

Filtrar:

SELECT *
FROM documento
WHERE cidade = 'Salvador';

Ordenar:

SELECT *
FROM documento
ORDER BY nome;

Agrupar:

SELECT cidade, COUNT(*)
FROM documento
GROUP BY cidade;

E, mais recentemente, executar operações de profiling e qualidade dos dados.

Ou seja, depois da importação, boa parte do problema já se parecia muito com um problema de banco de dados.

Então comecei a me perguntar:

Por que construir manualmente algo que um banco já sabe fazer?

Mas eu não queria um servidor de banco

Usar PostgreSQL resolveria boa parte dessas necessidades.

Só que criaria outras.

Para usar o Valtron, seria necessário ter um servidor disponível, configurar conexão, usuário, senha, banco, porta e pensar no ciclo de vida desses dados.

Para uma aplicação desktop, eu queria algo mais próximo disso:

abre o Valtron
      ↓
importa o arquivo
      ↓
trabalha com os dados

Sem uma etapa:

configure seu servidor de banco

É aí que o DuckDB encaixou muito bem.

DuckDB não precisa de um servidor

O DuckDB é um banco de dados embutido.

No Valtron, ele roda dentro da própria aplicação.

A arquitetura ficou aproximadamente assim:

┌─────────────────────────┐
│        Valtron          │
│                         │
│      TypeScript         │
│          ↓              │
│        Tauri            │
│          ↓              │
│         Rust            │
│          ↓              │
│        DuckDB           │
│          ↓              │
│     dados locais        │
└─────────────────────────┘

O frontend não abre uma conexão com um servidor externo.

Ele chama comandos Tauri, o backend Rust executa as operações e o DuckDB faz boa parte do trabalho relacionado aos dados.

O arquivo deixa de ser a estrutura de trabalho

Essa foi uma mudança importante no projeto.

Depois que um XLSX é importado, eu não quero continuar abrindo e percorrendo aquela planilha toda vez que o usuário fizer alguma coisa.

O fluxo é:

arquivo.xlsx
     ↓
  importação
     ↓
   DuckDB
     ↓
 consultas

Cada documento importado recebe uma tabela física própria dentro do banco local.

A partir daí, a fonte de trabalho passa a ser o DuckDB.

Isso significa que fazer um filtro não exige abrir novamente o XLSX.

Ordenar também não.

Executar SQL também não.

Fazer profiling também não.

O arquivo é a entrada. O banco passa a ser o ambiente de trabalho.

Isso ficou ainda mais interessante com a grid virtualizada

No post anterior falei sobre como a interface do Valtron não carrega centenas de milhares de linhas de uma vez.

Ela pede pequenas janelas.

É justamente o DuckDB que consegue responder essas solicitações.

Algo conceitualmente parecido com:

SELECT nome, cpf, cidade
FROM documento
WHERE cidade = 'Salvador'
ORDER BY nome
LIMIT 100
OFFSET 1200;

O frontend não precisa receber o dataset inteiro para descobrir quais são as linhas 1200 até 1299.

O banco faz isso.

A interface recebe apenas o resultado necessário naquele momento.

Isso criou uma separação que considero importante no Valtron:

DuckDB
sabe trabalhar com o dataset

       ↓

Rust
coordena as operações

       ↓

Frontend
sabe apresentar o resultado

SQL veio praticamente de graça

Quando os documentos passaram a existir como tabelas no DuckDB, apareceu outra possibilidade.

Se já existe um banco SQL por trás do Valtron, por que não permitir que o usuário consulte os documentos diretamente?

Foi assim que entrou o console SQL.

Hoje é possível executar consultas SELECT e CTEs sobre os documentos importados. O console é somente leitura, justamente para evitar que uma consulta digitada manualmente altere silenciosamente os dados.

Por exemplo:

SELECT
    cidade,
    COUNT(*) AS quantidade
FROM documento
GROUP BY cidade
ORDER BY quantidade DESC;

Isso adicionou uma característica que eu gosto bastante no projeto.

Quem não conhece SQL pode usar a interface.

Quem conhece SQL pode ir além dela.

Os dois trabalham sobre o mesmo conjunto de dados.

Depois veio o Data Profiling

Quando comecei a implementar análise de colunas, a escolha pelo DuckDB fez ainda mais sentido.

Imagine que eu queira saber sobre uma coluna NOTA:

quantos valores existem?
quantos estão vazios?
quantos são distintos?
qual o menor valor?
qual o maior?
qual a média?
como os valores estão distribuídos?

Eu poderia buscar 600 mil valores para o Rust e calcular tudo.

Mas seria estranho fazer isso tendo um motor analítico logo abaixo.

É muito mais interessante executar operações próximas dos dados:

604.270 registros
       ↓

O ganho real não é executar cinco operações de uma vez

Para mim, o ponto mais interessante das receitas não é economizar cinco cliques.

É transformar conhecimento sobre tratamento de dados em algo reproduzível.

Antes:

"Quando chegar a planilha,
lembre de remover os pontos do CPF,
corrigir os zeros,
converter a data..."

Depois:

Receita:
Tratamento de alunos

O procedimento deixa de existir apenas na cabeça de alguém.

Ele passa a existir como uma sequência executável.

E isso muda bastante o uso do Valtron

Sem receitas:

arquivo
   ↓
investigar
   ↓
corrigir
   ↓
exportar

Com receitas:

arquivo novo
   ↓
aplicar preparação conhecida
   ↓
validar resultado
   ↓
investigar exceções
   ↓
exportar

O trabalho humano começa a sair da parte repetitiva e ir para aquilo que realmente precisa de análise.

Esse é o ponto em que o Valtron começa a deixar de ser apenas uma ferramenta para trabalhar com um arquivo e passa a guardar como aquele tipo de dado deve ser preparado.

E isso abre outra possibilidade interessante.

Se consigo importar, transformar, validar e exportar seguindo uma receita, o próximo passo pode ser deixar de pensar apenas em arquivos.

Por que a entrada precisa ser sempre XLSX ou CSV?

Por que a saída precisa ser sempre outro arquivo?

No próximo post quero explorar essa ideia: como conectores com PostgreSQL, Parquet e outras fontes poderiam transformar o Valtron de um Data Preparation Studio baseado em arquivos em uma ferramenta local para movimentação e preparação de dados entre diferentes fontes.
